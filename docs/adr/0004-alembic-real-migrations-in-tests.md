# ADR-0004 — Alembic migrations, exercised by the real test suite

- **Status:** Accepted
- **Date:** Reconstructed 2026-07-28 (original decision predates this record)

## Context

Schema changes need to be versioned and applied reproducibly across dev, CI, and
prod. A common shortcut is to build the test database from
`SQLModel.metadata.create_all()` — but that bypasses the migrations, so tests can
pass against a schema that the real migrations would never produce (wrong column
types, missing partial indexes, different FK/ON DELETE behavior).

## Decision

Use **Alembic** for all schema changes. The **test suite applies the real
migrations** (not `create_all`) against a throwaway `practice_journal_test`
database created and dropped per run.

## Rationale

- Tests exercise the exact schema prod will have — column types, partial
  indexes (ADR-0015), FK `ON DELETE` rules, and constraints all match.
- Autogenerated migrations are reviewed before commit, so surprises surface at
  authoring time, not deploy time.
- Railway runs `alembic upgrade head` on deploy, so the same migration path runs
  everywhere.

## Alternatives considered

- **`create_all` for tests** — faster to set up, but decouples tests from the
  real schema; rejected for the reasons above. *(Reconstructed.)*
- **No migrations (recreate schema)** — untenable for a deployed app with data.

## Consequences

- Tests need a live Postgres (`conftest.py` resolves `DB_HOST`), so they run in
  the container.
- After changing a model, you must generate and review a migration; the migration
  is part of the change, and CI will run it.
